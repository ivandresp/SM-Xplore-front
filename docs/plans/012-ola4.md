## Bloques

### B1 — Duplicados + caché (cerrado)

- **Cambio:** `src/services/cache.ts` (TTL 30 s, dedupe en vuelo, generación, tope 200) integrado
  en `httpClient` para GET/HEAD; clave con huella del token; mutaciones invalidan salvo
  `POST /interactions/view/**`; `saveToken`/`clearToken` vacían. `src/test/setup.ts` limpia entre tests.
- **Resultado:** montar 8/8/8/6/8 → **4/4/4/3/4**; volver 6/6/6/4/6 → **0**; `/app` admin 3 → **0**;
  build de producción, volver 0. Medidor reproducible: `node scripts/measure-requests.mjs`.
- **Decisión de contrato:** el gateway manda `Cache-Control: no-store` en toda respuesta. Esta caché
  es estado de aplicación (por pestaña, ligada al token, se vacía al cambiar de sesión), no una caché
  HTTP, así que **no lo obedece a propósito**. Si el equipo quiere semántica HTTP estricta, se quita
  ese header en los GET públicos desde backend.
- **Auditoría:** independiente y adversario, ambos **PASA CON RESERVAS** sobre `41c3237`; `3b76afb`
  cierra sus reservas bajas con test (huella del token, aborto previo, `AbortSignal` sin dedupe,
  regex anclada, rejuvenecimiento). Ese último commit no tiene firma nueva: así consta.
- **No probado:** Safari/Firefox, dos cuentas reales en navegador (sí test determinista), 403/429/500
  reales en `/app`, build de producción «antes».

### B5 — Recomendaciones: latencia, error, filtros y preferencias (en curso)

- **Diagnóstico ya hecho:** caliente 15 ms; frío 0,74 s; 6,5 s solo en arranque con locks de Neo4j.
  El error genérico no se reproduce con el backend actual; el defecto real es que se descarta el
  `cause` y el mensaje apunta a una consola que no tiene nada.
- **Cambio:** registrar el error real (código/estado/campo) sin mostrar `detail`; ajustar el schema
  con el payload real delante; preferencias editables en el perfil; filtro/paginado explícito o
  «ver más» con el contrato real de ms-05 (`limit`).
- **Aceptación:** p95 < 1,5 s caliente y < 2,5 s frío, 5 muestras; renderiza con 0, 1 y muchas
  preferencias; test con el payload que rompía; en pantalla se ve por qué se filtró y cuántos hay.
- **Riesgo:** maquillar la latencia con un spinner. Se mide antes/después con `curl` y marca de
  tiempo en el navegador.
- **Skills:** `systematic-debugging`, `vercel-react-best-practices`, `api-designer` si cambia el endpoint.

### B2 — Combobox propio, estado activo, padding

- **Cambio:** `Select` con patrón combobox/listbox ARIA 1.2 que sustituya los `<select>` nativos;
  en el header, ruta activa con `aria-current="page"` y estilo persistente.
- **Aceptación:** teclado completo (Tab, flechas, Home/End, Esc, Enter), `aria-expanded`,
  `aria-activedescendant`, foco visible, padding de flecha igual al input, claro/oscuro; sin romper
  `label`/`id`.
- **Fuera:** el input de fecha nativo se queda igual.
- **Riesgo:** migrar 20+ usos de golpe. Misma API que `Field`/`SelectField` y migración por lotes.

### B3 — Validación del registro

### B4 — Reportes: ubicación y foto

### B8 — Guías y gestoras + onboarding (diseño aprobado)

**Backend ms-01 (primero, sin él no hay front):**

- `POST /auth/register/guia` (nombre, correo, teléfono, contraseña, DNI, licencia) → usuario
  `GUIDE` con estado de registro `PENDIENTE`. Hoy `registrationStatus` solo existe en
  `PrestadoraServicios.java:16`; hay que dárselo a `Guia` (o generalizar el enum
  `ProviderRegistrationStatus` a un `RegistrationStatus` compartido).
- Mientras esté `PENDIENTE`, la cuenta no entra: `status = SUSPENDIDO` o equivalente (el login solo
  mira `isActive()` → `status == ACTIVO`, `Usuario.java:92`).
- **Mensaje específico de admisión:** solo cuando la contraseña es correcta y el estado es
  `PENDIENTE` → 403 con código estable `ACCOUNT_PENDING_REVIEW` («Tu solicitud como guía está en
  revisión. Te avisaremos por correo cuando la aprobemos o la rechacemos.»). Contraseña incorrecta o
  cuenta bloqueada de verdad → sigue `INVALID_CREDENTIALS`. No permite enumerar cuentas: la rama
  se evalúa después de verificar la contraseña (`LoginService.java:77-96`).
- `POST /admin/users/{id}/guide-review` con `{decision: APROBADO|RECHAZADO, reason ≤ 500}` → 204.
  Se puede generalizar el actual `provider-review` (`ProviderReviewRequest.java:7`) porque la
  máquina de estados es la misma (`PENDIENTE/APROBADO/RECHAZADO`).
- Correos: «solicitud recibida» al registrarse; aprobado/rechazado con motivo, reutilizando el
  patrón de `EmailProviderReviewNotifier.java:32-49`. Mailpit local: SMTP `:1025`, UI
  `http://127.0.0.1:8025`; en producción solo cambia el host.
- Gestoras: mismo flujo de registro público + aprobación (decisión 4). Si se prefiere invitación de
  admin, ya existe `POST /admin/users/{id}/password-reset` como invitación.

- **Riesgo:** reutilizar `provider-review` sin generalizar el estado; permitir login antes de aprobar.
  Mitigación: estado propio del guía + test de los tres casos de login.

## Protocolo para agentes

1. Leer `AGENTS.md`, `docs/agents/prompt-senior.md` y este archivo antes de tocar nada.
2. Un bloque = una rama desde `origin/develop` = un PR. Nada directo a `develop`; el merge necesita
   review de otra persona. No hay CI en el repo front: la puerta es local
   (`typecheck && lint && test && build`).
3. Briefing de subagente con los 7 campos de §4.2 y sus skills cargadas antes de la primera acción.
4. Auditoría por otro agente (nunca el autor); en B1, B5 y B8 también independiente.
5. Al cerrar: actualizar la tabla de estado, el resultado del bloque y «no probado» en este archivo.
6. Lo que no se midió se declara; no se rellena con suposiciones.
